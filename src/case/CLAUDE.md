# Feature module conventions (using `case/` as the example)

- File structure ("Code structure: one concern per file" in the root `CLAUDE.md`): `case.controller.ts` and `case.service.ts` contain only their class. Constants (`LIST_ITEM`, `DETAIL`, `FULL`, `LANG_QUERY`, `SLUG_PARAM`, `MAX_IMAGE_BYTES`) live in `case.constants.ts`, types in `case.types.ts`, pure helpers in `case.util.ts` (with a spec), one DTO per file in `dto/`.
- Layers: `*.controller.ts` (routing only, no logic) → `*.service.ts` → `PrismaService`. The controller never touches the DB directly.
- DTOs live in `dto/`: classes with class-validator decorators and `!` on fields. The global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) is set up in `configureApp()`, so a field without a decorator is rejected. Enums come from `src/prisma/enums.ts`.
- New DB model: add it to `prisma/contract.prisma`, run `pnpm run db:generate`, then add a getter to `src/prisma/prisma.service.ts` (like `get cases()`).
- Queries use the Prisma 8 ORM style: `.create({...})`, `.first({ slug })`, `.where({ published: true }).orderBy([row => row.sortOrder.asc(), row => row.createdAt.desc()]).all()`. Don't use the old `findMany({ where })` shape.
- Register the module in `AppModule`; import `PrismaModule` wherever DB access is needed.
- Imports are sorted automatically (`simple-import-sort`); unused ones are removed by the linter.
- The service returns a row plus the computed picture URL (`CaseView` / `CaseFullView` in `case.types.ts`, built in `CaseService.toView` / `toAdminView` from `StorageService.publicUrl(imageKey)`); the response shape is set by the controller: `@SerializeOptions({ type: CaseListItemDto | CaseDetailDto | CaseFullDto, strategy: 'excludeAll' })` plus the global `ClassSerializerInterceptor` from `configureApp()`. Only fields marked `@Expose()` in the response DTOs reach the client, so a new field must get `@Expose()` (and `@ApiProperty`, there is no Swagger plugin), otherwise it silently disappears. Dates are flat `startedAt` / `endedAt`. The shape is covered by `dto/case-serialization.spec.ts` and the e2e key lists.
- Access: the global `AdminGuard` protects every route of this controller. Only the two reads carry `@Public()`; every other route needs the admin token and must have `@ApiAdminAuth()` (see "API documentation" in the root `CLAUDE.md`). Do not add `@Public()` to a write route, and put it on a new read only if it must be open to everyone. Unauthenticated requests get `401` before the DTO is validated or the case is looked up, so an unknown slug is also `401` without a token.
- Public reads filter `published: true`; an unknown and an unpublished slug give the same `404`. Writes (`PATCH`, `DELETE`) ignore `published`.
- Update/delete use `.whereUnique({ slug }).update(...)` / `.delete()`, which return `null` when no row matches (map that to `NotFoundException`). Do not catch database errors in the service: a duplicate slug (unique violation) is translated to `409` by the global `AllExceptionFilter` (see "Error handling" in the root `CLAUDE.md`). `undefined` fields in `update` are left unchanged, `null` clears.
- `UpdateCaseDto` is `PartialType(OmitType(CreateCaseDto, ['slug', 'translations']))` from `@nestjs/swagger` plus `translations?: UpdateCaseTranslationsDto` (per-language `PartialType(CaseTranslationDto)`); `slug` is immutable.
- Localization: the text (`name`, `category`, `shortDescription`, `description`, `achievements`) lives in `case_translations` (`CaseTranslation`, composite key `(caseSlug, locale)`, `onDelete: Cascade`); `cases` has no text columns. Locales are `SUPPORTED_LOCALES` (`ru`, `en`), `DEFAULT_LOCALE` is `ru`. Public reads: `@Query('lang')` goes through `resolveLocale` (`case-locale.util.ts`, only the exact `en` selects English, never a `400`), the service loads `.include('translations')` and builds a flat `CaseView` with `selectTranslation` (requested language, else `ru`) and `locale`; a published case with nothing to serve is skipped in the list and is a `404` in the detail instead of a `500`. Writes return `CaseFullView` (`CaseFullDto`: shared fields, `published`, `sortOrder`, `translations: { ru, en }` with `null` for a missing language, no `locale`).
- Writes with translations run in `PrismaService.transaction`. `createCase` creates the row and one translation per given language. `updateCase` reads the case with its translations, merges per language and per field in memory (`achievements` replaced as a whole, a missing language must come complete or it is a `400`), checks the publish rule on the resulting state (`canBePublished`: every `SUPPORTED_LOCALES` entry present, else `400` with `PUBLISH_NEEDS_ALL_LANGUAGES`), and only then writes. Pure helpers (`pickText`, `isCompleteText`, `textsByLocale`, `omitUndefined`, ...) are in `case-translation.util.ts`. `setImage` returns the admin view (translations are read before any storage side effect); `deleteCase` relies on the cascade.
- The migration `add_case_translations` copies the old text into `ru` rows, sets `published = false` on every case (nothing may be public without `en`) and only then drops the old columns; it is applied by the user (`db:migrate`), never by the agent.
- Pictures: the DB columns `imageKey` / `blurImage` are written only by `setImage` / `removeImage` (`PUT` / `DELETE /cases/:slug/image`), never through the JSON DTOs. `imageKey` stays internal: it has no `@Expose()` and must not appear in Swagger; clients get `image` (the URL) and `blurImage`. `setImage` order matters: look the case up (404 before any work) → `ImageProcessingService.process` (400) → `StorageService.put` under `cases/<slug>/<sha256 prefix>.webp` → update the row (on failure delete the new object unless it is the one the case already uses) → delete the previous object. Deleting an object is best effort (`removeObject` logs a warning and swallows the error); `deleteCase` and `removeImage` use the same helper. Keep the order when changing it: the case must never point at a missing object.
- Test fixtures for rows live in `case.fixtures.ts` (`caseRow` for a DB row, `caseView` for what the service returns; excluded from coverage).
- Swagger documentation is mandatory for every endpoint and DTO field of this module (see "API documentation (Swagger)" in the root `CLAUDE.md`): operation text, `@ApiParam`, all response statuses with `ErrorResponseDto`, `@ApiProperty` with description, example and constraints. `test/api-docs.e2e-spec.ts` fails if a request schema is empty or an error status is undocumented.
