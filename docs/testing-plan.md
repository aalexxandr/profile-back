## 1. Цель и границы

**Цель.** Подготовить инфраструктуру, инструкции и скиллы так, чтобы при реальной разработке тесты писались автоматически: ИИ сам пишет тест вместе с новым кодом, а разработчик видит готовый образец и проверяет результат.

**Границы.**

- Модуль `case` (контроллер, сервис, DTO) **тестовый и будет удалён**. Тесты для него не пишем и баги в нём не чиним в рамках этого плана. Ни помощники, ни образцы, ни документация не должны на него опираться.
- Тесты пишем только на то, что останется: общая настройка приложения и инфраструктурный код.
- Любой пример в документации и скилле использует нейтральные имена (`<module>`, `Create<Name>Dto`), а не `case`.

**Где мы сейчас.**

- В проекте нет ни одного теста. E2E-тест удалили при миграции на Prisma 8 (коммит `a14ade6`).
- CI зелёный только из-за `--passWithNoTests` (в `pnpm test` и в шаге e2e).
- `testRegex` в `package.json` ловит и `*.spec.ts`, и `*.e2e-spec.ts`. Когда появится первый e2e, `pnpm test` (и `pnpm run check`) начнёт ходить в БД. В CI `pnpm test` идёт до `db:init`, поэтому шаг упадёт.
- Уже добавлено: правило про тесты в `CLAUDE.md`, `test/CLAUDE.md`, `README.md` и скилл `.claude/skills/writing-tests/SKILL.md` (его примеры нужно сделать нейтральными, см. шаг 4).

## 2. Принципы

1. Тест проверяет **поведение** (что видит клиент API), а не внутреннее устройство.
2. Не мокаем то, что можно проверить по-настоящему. Цепочку Prisma 8 ORM (`.orderBy().all()`) не мокаем, её проверяет e2e на реальной локальной БД.
3. Unit-тесты быстрые: без сети и БД. E2E изолированы: уникальные данные, сами за собой убирают.
4. Тест падает, когда ломается поведение, и не падает от безобидного рефакторинга.
5. Один тест проверяет одну вещь. Название описывает ожидание: `возвращает 404, если запись не найдена`.
6. Тесты не зависят друг от друга и от порядка запуска.
7. Правила максимально механические, чтобы ИИ мог их выполнять без угадывания: «если изменили X, пишем тест Y в файл Z».

## 3. Пирамида тестов

| Уровень | Что проверяет                                                                                  | Где лежит                 | БД                                        | Запуск                          |
| ------- | ---------------------------------------------------------------------------------------------- | ------------------------- | ----------------------------------------- | ------------------------------- |
| Unit    | DTO-валидацию, фильтры, пайпы, guard, чистые функции, сервисы с логикой                        | `*.spec.ts` рядом с кодом | нет                                       | `pnpm test`                     |
| E2E     | Эндпоинты целиком: HTTP → ValidationPipe → контроллер → сервис → фильтр (и БД, если она нужна) | `test/*.e2e-spec.ts`      | локальная, только если тест её использует | `pnpm run test:e2e --runInBand` |

Сервисы с ветвлением и расчётами тестируем unit-тестом с типизированным моком `PrismaService`. Тонкие сервисы-прокладки отдельно не тестируем: их покрывает e2e.

E2E бывают двух видов:

- **Без БД**: свой набор controllers/providers (заглушки) поверх `configureApp()`. Быстро и стабильно, подходит для проверки общей настройки и для образца.
- **С БД**: `AppModule` целиком и реальная локальная БД. Для эндпоинтов, где важен запрос к Prisma.

## 10. Правила на будущее (для разработки)

Новая функциональность, которую стоит покрыть тестами, **покрывается тестами в том же изменении**. Для написания используйте скилл `writing-tests`.

Что считаем «стоит покрыть»:

- новый эндпоинт → e2e на успешный путь, невалидный ввод, «не найдено/конфликт»;
- новое DTO или изменение правил валидации → unit-тест граничных значений (максимум проходит, максимум + 1 нет);
- новая бизнес-логика в сервисе, фильтр, пайп, guard, interceptor → unit-тест;
- исправление бага → сначала тест, который воспроизводит баг (красный), потом исправление.

Что не требует теста: правки документации и конфигов, переименования без смены поведения, пустые заглушки без логики.
