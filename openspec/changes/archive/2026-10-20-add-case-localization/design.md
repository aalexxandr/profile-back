# Design

## Context

See proposal.md for motivation and the specs for the required behavior.

Current state: `cases` holds all fields, including the text. `CaseService` returns a DB row plus a computed `image`, and the response shape is chosen by `@SerializeOptions` with `CaseListItemDto` / `CaseDetailDto` (`strategy: 'excludeAll'`, only `@Expose()`d fields are sent). `CreateCaseDto` carries the text fields at the top level and `UpdateCaseDto` is `PartialType(OmitType(CreateCaseDto, ['slug']))`. Prisma is 8 (release candidate): no client, a contract file, a new query style, migrations generated by `db:migration:plan` and committed. The agent must not run DB-mutating commands; the user applies migrations.

## Goals / Non-Goals

**Goals:**

- Store the text per locale in a table with database-level guarantees (unique per case and locale, cascade delete).
- Keep the public response shape flat, so the frontend only adds `?lang=` and reads `locale`.
- Enforce "published means both languages" in one place (the service), on the resulting state.

**Non-Goals:**

- A third locale, per-locale `slug`, localized validation messages, `Accept-Language` negotiation, translating `company`, `stack` or the `role` enum (the frontend maps `role` through its own i18n).
- An admin read endpoint for drafts (there is none today; the admin sees a case through the write responses).
- Removing a translation.

## Decisions

### Data model: `case_translations`

```
cases (language-independent)          case_translations
+------------------------+            +--------------------------------+
| slug PK                |<-----------| case_slug FK  (on delete cascade)
| project_link, stack    |            | locale   enum('ru','en')       |
| role, company, team... |            | name, category                 |
| started_at, ended_at   |            | short_description, description |
| sort_order, published  |            | achievements  Achievement[]    |
| image_key, blur_image  |            | PRIMARY KEY (case_slug, locale)|
+------------------------+            +--------------------------------+
```

`locale` is a native enum (`Locale { RU = "ru", EN = "en" }`) like `Role`, so the database refuses a third value. The composite type `Achievement` is reused as the column type of `achievements`. The text columns are dropped from `cases`. Alternatives rejected: duplicated columns (`name_ru`, `name_en`; a third language needs a schema change and `achievements` must be duplicated), JSONB per field (no NOT NULL / length guarantees, unproven in Prisma 8 RC).

**Spike findings (Prisma 8.0.0-rc.18, from the docs bundled in `node_modules/@prisma/orm-postgres/skills/prisma-8`):**

- (a) Relations are declared on the owning side with `@relation(fields: [...], references: [...], onDelete: Cascade)`; the default is `Restrict`, so `onDelete: Cascade` must be written. `@@unique`, `@@id([a, b])` and `@@index` are available. A list of value objects (`Achievement[]`) is stored as one `jsonb` column, exactly as today in `cases`. The project keeps its existing `pg.enum(...)` / `native_enum` syntax for `Locale`.
- (b) Related rows load with `.include('translations', (t) => t...)` on the ORM collection; the branch accepts `where` / `select` / `orderBy`. No second query is needed.
- (c) `db.transaction(async (tx) => { tx.orm.public.X.create(...) })` commits on return and rolls back on a throw. `PrismaService` does not expose it yet, so it gets a `transaction(fn)` method (a pass-through to `client.transaction`).
- (d) A data step is `this.dataTransform(endContract, name, { check, run })` or the raw escape hatch `rawSql({ id, label, operationClass, target, precheck, execute, postcheck })`. The typed builder works against the end contract only, which no longer has the old text columns, so the copy from `cases` into `case_translations` is written as `rawSql` (`INSERT ... SELECT`). The operations list of the generated `migration.ts` is edited by hand into the order create table -> copy -> unpublish -> drop columns, then self-emitted with `node <package dir>/migration.ts`. `db migrate` runs the whole run in one Postgres transaction, so a failure in any step rolls back everything, including the copy.

### Locale resolution is a pure function

`resolveLocale(raw: unknown): Locale` returns `en` only for the exact string `en`, otherwise `ru`. The controllers read `@Query('lang')` as a plain string and do not validate it with a DTO, so an unknown value can never produce `400`. It lives in a `*.util.ts` with its own spec (`Accept-Language` is simply never read). The `lang` parameter is documented with `@ApiQuery` (enum, default `ru`).

### Reads join the translation and return a flat view

The service loads the case with its translations and builds `CaseView = language-independent fields + the chosen translation + locale + image`. The published invariant means the requested translation exists; as a defensive measure the service falls back to the `ru` row if the requested one is missing and reports `locale: 'ru'` in that case, instead of failing with `500`. The serializer DTOs keep `strategy: 'excludeAll'` and gain an `@Expose()`d `locale`.

### Writes: DTO split and one transaction

- `CreateCaseDto` holds the language-independent fields plus `translations: CreateCaseTranslationsDto` (`ru` required, `en` optional, both `CaseTranslationDto`; the limits moved from the old top-level fields).
- `UpdateCaseDto` is `PartialType(OmitType(CreateCaseDto, ['slug', 'translations']))` plus `translations?: UpdateCaseTranslationsDto` whose locales are `PartialType(CaseTranslationDto)`. Nested objects use `@ValidateNested` + `@Type`, so `whitelist` / `forbidNonWhitelisted` reject unknown fields and unknown locales (`de`) at every level.
- The service creates the case and its translation rows in one transaction, and `PATCH` merges into the existing rows in one transaction. A locale with no row yet is created only when the merged object is complete, otherwise `400` (a complete check on the merged object, not a DTO rule, because it depends on the stored state).
- Publish rule in the service, on the resulting state: after merging, `published && !(ru && en)` throws `BadRequestException`. Unique violations still propagate to the global filter (`409`); services do not catch database errors.

### Full view

`CaseFullDto` (returned by `POST`, `PATCH`, `PUT /image`) has the language-independent fields, `published`, `sortOrder`, `image`, `blurImage` and `translations: { ru: TranslationDto | null, en: TranslationDto | null }`. Assumption: `published` and `sortOrder` are included because an editor of both languages needs them, and today's detail view hides them only because it is public. It has no `locale`. Alternative rejected: `?lang=` on write endpoints returning the flat shape, which hides the other language from the editor.

### Data migration

The migration must be written as: create the table and enum, copy `name`, `category`, `short_description`, `description`, `achievements` of every `cases` row into `case_translations` with `locale = 'ru'`, set `published = false` on all cases, then drop the old text columns. The order matters (copy before drop). Because Prisma 8 RC may not generate the data step, it is planned and reviewed as a spike first (see tasks); it is applied by the user, not the agent. Rollback: restore from a backup taken before the migration; there is no down migration for the dropped columns.

## Risks / Trade-offs

- [Prisma 8 RC may lack ergonomic relations, transactions or a data step in migrations] → the first task is a spike against the real contract (a throwaway test, no schema change committed until it works); fall back to two queries inside one transaction instead of a join if relation loading is unavailable.
- [Existing published cases disappear from the public list until `en` is added] → intended and agreed; the user fills `en` through `PATCH` before re-publishing.
- [Breaking API for the admin client and for generated frontend types] → documented in Swagger; the frontend regenerates types from `/docs-json`.
- [A third locale later] → requires a new enum value and a migration, and the "published needs all locales" rule becomes "all supported locales"; accepted for two languages.
- [Data loss if columns are dropped before the copy] → the migration order and a manual check on a copy are part of the tasks.
