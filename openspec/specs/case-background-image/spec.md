# case-background-image Specification

## Purpose

Defines how a case gets its background picture: a single uploaded image is re-encoded to an optimized WebP in the S3 bucket, a blur placeholder is generated into the database, and the API exposes both to the frontend as `backgroundImage` and `backgroundBlurImage`, independently of the case picture.

## Requirements

### Requirement: Upload a case background

`PUT /cases/:slug/background` SHALL accept a `multipart/form-data` body with exactly one file field `file`, store an optimized copy of the picture as the background of the case, and respond `200` with the full view of the case (see `case-management`) including `backgroundImage` and `backgroundBlurImage`. The route MUST work for published and unpublished cases and MUST NOT change `image` or `blurImage`. Publishing a case MUST NOT require a background.

#### Scenario: Upload a JPEG background

- **WHEN** a case `spectre` exists and a client sends `PUT /cases/spectre/background` with a valid JPEG in the field `file`
- **THEN** the response is `200` and `backgroundImage` is an absolute `http(s)` URL ending in `.webp`
- **AND** `backgroundBlurImage` is a string starting with `data:image/webp;base64,`
- **AND** the response contains `translations`

#### Scenario: Background is independent of the case picture

- **WHEN** a case `spectre` has an `image` and a client uploads a background for it
- **THEN** `image` and `blurImage` in the response equal their previous values

#### Scenario: Upload to a draft

- **WHEN** a case `draft` with `published = false` exists and a client sends `PUT /cases/draft/background` with a valid PNG
- **THEN** the response is `200`

#### Scenario: Unknown case

- **WHEN** a client sends `PUT /cases/does-not-exist/background` with a valid JPEG
- **THEN** the response is `404`
- **AND** nothing is written to the storage

#### Scenario: File field is missing

- **WHEN** a client sends `PUT /cases/spectre/background` as multipart without the field `file`
- **THEN** the response is `400`

### Requirement: Process the background like the case picture

The background SHALL be accepted, validated and re-encoded by the same rules as the case picture (`case-image`): JPEG, PNG and WebP recognised by content, a corrupted or other file rejected with `400`, a file over 10 MB rejected with `413`, the result a genuine WebP at most 1920 px wide, never enlarged, orientation applied, metadata removed. The blur placeholder MUST be generated by the server from the same upload and MUST be a `data:image/webp;base64,...` URI. A rejected upload MUST leave the case and the storage unchanged.

#### Scenario: Wide background is downscaled

- **WHEN** a client uploads a 4000x2000 JPEG to `PUT /cases/spectre/background`
- **THEN** the stored file is a WebP of 1920x960

#### Scenario: Text file renamed to an image

- **WHEN** a client uploads a text file named `bg.jpg` with `Content-Type: image/jpeg` to `PUT /cases/spectre/background`
- **THEN** the response is `400`

#### Scenario: File over the size limit

- **WHEN** a client uploads a file larger than 10 MB to `PUT /cases/spectre/background`
- **THEN** the response is `413`

#### Scenario: Rejected upload keeps the previous background

- **WHEN** a case already has a background and a client uploads an invalid file
- **THEN** the response is an error and `backgroundImage` and `backgroundBlurImage` of the case are unchanged

### Requirement: Store the background separately from the picture

The background object SHALL be stored in the bucket under `cases/<slug>/background/<content hash>.webp`, the database SHALL keep only that key and the blur placeholder, and responses MUST expose the absolute URL (public base URL plus key) and never the key. Replacing the background MUST store the new object and save the row before the previous object is removed; a failure MUST NOT leave the case pointing at a missing object. Uploading the same file again MUST change nothing.

#### Scenario: Replace the background

- **WHEN** a case has a background and a client uploads a different valid image
- **THEN** `backgroundImage` points to a new URL and the previous object no longer exists in the storage

#### Scenario: Same file twice

- **WHEN** a client uploads the same file to `PUT /cases/spectre/background` twice
- **THEN** both responses have the same `backgroundImage` and the object still exists

#### Scenario: Failed save keeps the case consistent

- **WHEN** the row update fails after the new object was stored
- **THEN** the new object is removed (unless it is the one the case already uses) and the case still points to its previous background

#### Scenario: Storage key is not exposed

- **WHEN** a client reads a case that has a background in any view
- **THEN** the response has no `backgroundImageKey`

### Requirement: Remove a case background

`DELETE /cases/:slug/background` SHALL clear `backgroundImage` and `backgroundBlurImage` of the case, remove the stored object and respond `204`. Repeating the call for a case without a background MUST also answer `204`. An unknown case MUST answer `404`. The case picture MUST stay unchanged.

#### Scenario: Remove an existing background

- **WHEN** a case has a background and a client sends `DELETE /cases/spectre/background`
- **THEN** the response is `204`, the stored object no longer exists and the case has `backgroundImage = null` and `backgroundBlurImage = null`
- **AND** `image` and `blurImage` of the case are unchanged

#### Scenario: Remove when there is none

- **WHEN** a case without a background receives `DELETE /cases/spectre/background`
- **THEN** the response is `204`

#### Scenario: Remove for an unknown case

- **WHEN** a client sends `DELETE /cases/does-not-exist/background`
- **THEN** the response is `404`

### Requirement: Background routes require the admin token

`PUT /cases/:slug/background` and `DELETE /cases/:slug/background` SHALL require the administrator token (see `admin-auth`) and respond `401` without a valid one, before the upload is parsed or stored.

#### Scenario: Upload without a token

- **WHEN** a client sends `PUT /cases/spectre/background` with a valid JPEG and no `Authorization` header
- **THEN** the response is `401` and nothing is written to the storage

#### Scenario: Delete with a wrong token

- **WHEN** a case has a background and a client sends `DELETE /cases/spectre/background` with `Authorization: Bearer wrong-token`
- **THEN** the response is `401` and the background is unchanged
